# Swift coordinator parity

Run from the repository root with Python 3.11 or later as the HTTP client. Each stage starts an ephemeral loopback listener. Pairing and team tests create credentials in a private temporary directory and remove the test database on exit. The default candidate is the Swift service.

| Stage | Command | Evidence |
| --- | --- | --- |
| Bootstrap | `python3 qa/swift_service_parity.py status` | Runs the existing exact status probe against `swift run tachi-coordinator --port 0` and verifies the v1 unknown-route response. |
| Pairing | `python3 qa/swift_service_parity.py pairing --legacy-root /path/to/previous-checkout` | Runs the existing client-pairing checks with the Swift operator CLI. Then runs a cutover and restart using an existing Python coordinator database. |
| Reference teams | `python3 qa/swift_service_parity.py reference-teams` | Runs the existing sibling-client, cross-human isolation and pending-work revocation check against the opt-in Swift reference-team service. Assistant work in this stage is synthetic. |
| Solo routine | `python3 qa/swift_service_parity.py solo --service-root /path/to/candidate` | Drives paired clients through the Swift solo routes to a disposable loopback webhook. Checks acceptance, observed rejection and loss of the reply across a process restart. |
| Enrolled routine | `python3 qa/enrollment_http.py --service-root /path/to/candidate --coordinator /path/to/tachi-coordinator --accounts /path/to/tachi-accounts` | Builds a small grant provisioner against the candidate Grok package. Runs the three solo HTTP checks with that directory, then with the original private JSON file, using the same compiled coordinator. Both runs use disposable literal-loopback destinations. |
| Human workspaces | `python3 qa/swift_service_parity.py workspaces --service-root /path/to/candidate` | Pairs two humans and verifies room and DM history after membership revocation, rejoin and restart. |
| Workspace artifacts | `python3 qa/swift_service_parity.py artifacts --service-root /path/to/candidate` | Uploads synthetic documents over paired HTTP and checks bytes and SHA-256 after restart, direct audiences, source references and both workspace quotas. |
| Workspace assignments | `python3 qa/swift_service_parity.py assignments --service-root /path/to/candidate` | Checks owner consent, member assignment and revocation with a private loopback routine. Pauses one binding across restart while another workspace dispatches. Counts each POST and verifies that resume preserves sender authority, accepted receipts and uncertainty after a dropped reply. |
| Workspace export | `python3 qa/swift_service_parity.py export --service-root /path/to/candidate` | Compares a paired human’s complete export with visible messages and each document GET, including exact bytes across revoke/rejoin. Checks each limit at equality and overflow for participants with different audiences. |

Use `--service-root` to build and run a candidate from a separate checkout while retaining this QA driver. `--legacy-root` selects the historical Python source used to produce the database. For reproducible pairing evidence use a checkout or source archive of the original [pairing revision](https://github.com/Section9Labs/tachi/commit/10ee2490090156d521392401199ce475695ac030) and record both revisions. The default producer is the working directory. Add `--python-control` to any stage to validate the oracle using Python on the candidate side. Record that run separately from Swift results.

The cutover test first creates two legacy clients of the same human, revokes one, and leaves an unredeemed invitation for a second human. After the old server exits, the candidate opens that exact SQLite file. It must resolve the surviving bearer with its original client ID and scopes, reject the revoked bearer and consumed invitation, and redeem the pending invitation. The candidate operator revokes the original surviving client. A second candidate process must still reject both revoked bearers and the re-used invitation, and resolve the new client with its original identity and scopes. No schema or fixture rows are constructed by the test.

The solo stage provisions one private operator file and SQLite database per case. The listener records the POST path, whether the synthetic bearer matched, and the JSON body. It either returns HTTP 200 or 503, or closes the connection after reading the POST and before sending headers. After restarting the coordinator on the same file, a sibling retries the same task ID. The stage checks the stored snapshot, a conflict on a changed payload, per-user access and the total number of POSTs. A read-only check of the stopped database counts the stored delivery and verifies the single acceptance or rejection event, or zero events after a lost reply. Each task snapshot must report `native_result_available: false` and `result: null`. Native session identity, in-provider action and result retrieval require the separate [solo and team acceptance runs](../docs/acceptance/README.md#solo-attachment-and-retrieval).

The artifacts stage uses private temporary databases. Its boundary case sends a slash-escaped JSON representation of exactly 1 MiB of binary data and compares the downloaded bytes. The byte-quota case stores 64 MiB and the count-quota case stores 256 empty artifacts. Both retry the original ID at the limit. A trusted Python TeamQueue writer supplies one room task as a source reference using the paired human’s authority. The coordinator handles every artifact upload and retrieval over HTTP. The tests use synthetic content and perform no provider dispatch.
